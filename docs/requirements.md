# taski 要求仕様

本ドキュメントは taski が **何を** 満たすかを定める。実装の現状を反映した「あるべき仕様」の記述であり、個々の実装詳細ではなく満たすべき要件を示す。

- **[architecture.md](architecture.md)** — *どこに* 置くか（クレート構成・パイプライン・ビルド）
- **[syntax.md](syntax.md)** — *どう書くか*（記法。文書・行・行内）
- **[domain.md](domain.md)** — *何が何であるか*（概念・関係・導出。目標形）
- **[design.md](design.md)** — *どう表しているか*（現状の型・走査・不変条件・写像）
- **本ドキュメント** — *何を* 満たすか（要求）

ここには要求とその**根拠**（なぜその仕様なのか）を置く。記法の規範は syntax.md、概念の目標形は domain.md、型と不変条件は design.md が持ち、重複させない。

## 1. 概要・目的

- taski は、ワークスペースやユーザーのホーム配下に散在する Markdown ファイルからタスクを集約し、日付ごと・タグごとに整理して表示する VS Code 拡張である。
- タスクは元の Markdown ファイルへのクリック可能なリンクとして提示され、ソースへ即座に遷移できること。
- 同じ機能をターミナルから利用できる Rust 製 CLI (`taski`) を併せて提供する。
- UI 文字列・コードコメントは日本語とする。

## 2. タスク Markdown フォーマット要求

**書式の詳細は [syntax.md](syntax.md) が規範である。** ここには記法に対する*要求*（何を書けなければならないか、何を誤検出してはならないか）だけを置き、具体的な文法・正規化規則は重複させない。

### 2.1 タスクとログ

- タスクは 3 つの状態（未完了・完了・見送り）を持てること（[syntax.md §3.1](syntax.md#31-タスク行)）。
  - 見送りは「着手予定だったが着手できなかったもの」を表す。やらないと決めたか、翌日・inbox・nextAction などに同じものを積み替えた後にこの状態にする運用を想定する。表示上は「完了と同じく対応不要（クローズ済み）」として扱うが、完了とは区別する（[3.1](#31-treeview) 参照）。
- タスクに日付ごとのログを紐づけられること。帰属はインデントで表す（[syntax.md §4](syntax.md#4-インデントと帰属)）。
- ログを 1 つも持たないタスクは「日付なし」として扱う。
- コードブロック内のタスク・ログは解析対象から除外すること。ノートに記法の例を書けなくなるため。

### 2.2 ファイル単位の自動タグ

- front matter に `project: active` を持つファイルは、そのファイル名をタグとして全タスクに自動付与する（[syntax.md §5.2](syntax.md#52-タグ)）。PJ ノートに書いたタスクを、本文にタグを書かずにその PJ の名前で引けるようにするため。
- 本文中の `#tag` と自動タグは合算される。
- `project` が未指定、または `project: someday` / `project: done` の場合は自動タグを付与しない（`someday` は着手を棚上げしたプロジェクト、`done` は完了済みプロジェクトを示すメタ情報）。
  - この条件は「どの PJ か」（事実）に「表示するか」（判断）を混ぜているため、いずれ表示側の要求として書き直す（[design.md](design.md) G-1）。

### 2.3 PJ ノートの日報形式

- `note/` 配下のノートは front matter に `project:` を持つことでプロジェクト（PJ）ノートとして扱う。`repo:`（作業実体が別リポジトリにある場合のパス）と `completed:`（`done` のときの完了日）を任意で持てる。
- PJ ノートは「次の予定 / ログ / オープンタスク」の 3 セクションからなる日報形式とする（[syntax.md §8.2](syntax.md#82-pj-ノートのセクション規約)）。
- **チェックボックスを持つのは `## 次の予定` だけ**とする。これによりタスクとして解析される PJ 由来の行が「active な PJ につき最大 1 つ」に絞られる。
- `- [[ノート名]] ...` をチェックボックスと誤判定しないこと。
- タスク行末の括弧に判断メタデータ（所要時間・重さ・コンテキスト・締切）を書け、本文と分離して扱えること。単なる注記（`（仮）`）や列挙（`（髪・服・顔）`）を誤検出しないこと（[syntax.md §5.3](syntax.md#53-行末の括弧判断メタデータ)）。

### 2.4 時刻付きログ／スケジュール記法

- ログ行に時刻（開始のみ、または開始と終了）を付与できること。
- ジャーナルでは、日付見出しを持つ文書のトップレベル時刻メモをその日のスケジュール項目として扱う（[syntax.md §3.4](syntax.md#34-トップレベル時刻メモ)）。タスクに紐づかない予定・出来事を書けるようにするため。
- 時刻は 2 桁にパディングして正規化する。表示と比較を桁揃えのまま行えるようにするため。

## 3. VS Code 拡張の機能要求

### 3.1 TreeView

- 日付別ビュー（`taskiView` / 「タスク一覧」）: 日付 → ファイル → タスク → ログ の階層で表示する。
  - 並び順は「今日」を先頭とし、以降は新しい日付から古い順とする。
  - 「今日」は全タスク（完了・見送り含む）を進捗カウンタ付きで表示し、それ以外の日付は未完了タスクのみ表示する（完了・見送りは非表示）。
  - 見送り（`- [-]`）は「今日」ビューに表示するが、進捗カウンタ（`完了/総数`）の分母・分子どちらにも含めない中立状態として扱う。表示順は 未完了 → 完了 → 見送り とする。
- タグ別ビュー・スケジュール・アラートでは見送りを完了と同じく扱う（タグ別では非表示、スケジュールでは打ち消し線、アラート対象外）。
- タグ別ビュー（`taskiTagView` / 「タグ別」）: タスク本文の `#tag` とファイル単位の自動タグでグルーピングして表示する。
- 各ビューのタイトルから「更新」「同期（Git 自動同期有効時のみ）」「スケジュール表示」を操作できること。
- タスク／ログ項目のクリックで、元ファイルの該当行へ遷移できること。

### 3.2 コマンド

ユーザー向けコマンド:

- `taski.showToday` — 今日のタスクを表示
- `taski.refreshTasks` — タスクの再スキャン・再表示
- `taski.addTodayLog` — 今日の日付のログ行を追記（既定キー: Cmd/Ctrl+Shift+T）
- `taski.addTomorrowLog` — 明日の日付のログ行を追記（既定キー: Cmd/Ctrl+Shift+Y）
- `taski.toggleTask` — タスクの状態を切り替え（`[ ]` → `[x]` → `[-]` → `[ ]` の3状態サイクル、既定キー: Cmd/Ctrl+Shift+X）
- `taski.openTodayJournal` — 今日のジャーナルを開く
- `taski.syncNow` — Git を即時同期
- `taski.showSchedule` — スケジュールグリッドを表示
- `taski.openWikiLinkAtCursor` — カーソル位置の Wiki リンクを開く（既定キー: Cmd/Ctrl+Shift+O）

内部コマンド（コマンドパレット非表示）:

- `taski.openTaskLocation` — 指定ファイル・行を開く
- `taski.openWikiLink` — Wiki リンク先を開く

キーバインドは Markdown エディタにフォーカスがある場合のみ有効とする。

### 3.3 スラッシュ補完

- Markdown 編集中に `/today` `/tomorrow` `/now` を入力すると、それぞれ今日の日付・明日の日付・現在時刻を挿入する補完候補を提供する。
- すべての日付・時刻はローカルタイムゾーンで算出すること（UTC 不可）。

### 3.4 Wiki リンクナビゲーション

- Markdown 内の `[[foo]]` を Cmd/Ctrl+Click または専用コマンドで開けること。
- 解決優先順位: `$HOME/taski` > ワークスペース > 追加ディレクトリ > 開いているドキュメント。
- 一致する `foo.md` が存在しない場合は `$HOME/taski/note/foo.md` を `# foo\n` を初期内容として作成して開く。
- `[[YYYY-MM-DD]]` 形式はジャーナル `$HOME/taski/journal/<YYYY>/<MM>/<YYYY-MM-DD>.md` として扱う。
- `[[` 入力時に既存ノートを補完候補として提示すること。

### 3.5 スケジュールグリッド

- WebviewPanel で 15 分刻みのタイムグリッドを表示する。
- 表示時間帯は対象日のスケジュール項目に応じて動的に決定する。
- 計画（plan）と実績（actual）を対比できる構成とすること。

### 3.6 タスクアラート

- タスクの開始時刻が近づいた際に通知を表示する（`taski.taskAlert` で有効/無効）。
- 開始の何分前に通知するかを `taski.taskAlertLeadMinutes`（既定 1、最大 30）で設定できる。
- 定期的（30 秒間隔）に対象を判定し、同一タスクの重複通知を防止する。日付が変わったら通知済み状態をリセットする。

### 3.7 Git 自動同期

- `$HOME/taski` が Git リポジトリの場合、一定間隔で自動同期する（`add -A` → `commit` → `pull --rebase` → `push`）。
- ファイル保存時にもデバウンス付きで同期する。
- `taski.gitAutoSync` で有効/無効、`taski.gitSyncInterval`（秒、既定 60、最小 30）で間隔を設定できる。
- 変更がない場合はコミットをスキップする。同時実行を防止する。
- コンフリクト発生時は rebase を中断して作業ツリーを復元し、自動同期タイマーを停止してユーザーに通知する。ネットワークエラー時はログのみ記録し次回リトライする。

## 4. ファイルスキャン要求

- 既定で `$HOME/taski` が存在すれば常にスキャン対象とする（設定に依存しない）。
- 現在開いている Markdown ドキュメントは常にスキャン対象に含める。
- ワークスペースのスキャンは `taski.includeWorkspace`（既定 `false`）が有効な場合のみ行う。
- `taski.additionalDirectories`（絶対パス一覧）で追加スキャン対象を指定できる。
- `taski.excludeDirectories`（glob パターン一覧）でスキャン除外を指定できる。`node_modules` は常に除外する。

## 5. ジャーナル要求

- ジャーナルのパスは `$HOME/taski/journal/<year>/<month>/<YYYY-MM-DD>.md` とする。
- 必要なディレクトリは自動生成する。
- 拡張の `openTodayJournal` と CLI の `journal` サブコマンドで同一パス規約を用いること。

## 6. CLI (`taski`) 要求

- `parser-core` を直接利用し（WASM を介さない）、`clap` で構築する。
- サブコマンド:
  - `memo <text>` — 今日のジャーナルへ `- HH:MM: text` を追記。`--no-timestamp` で時刻接頭辞を省略。テキスト未指定かつパイプ入力時は stdin から読む。
  - `list` — 日付別にタスクを表示。`--format json|yaml` で構造化出力、`--tag <tag>` でタグ絞り込み。構造化出力の各タスクは原文（`text`）に加えて、判断メタデータを分離した `body` / `meta` を持つ（[syntax.md §5.3](syntax.md#53-行末の括弧判断メタデータ) と同一のルール。利用側に同じ判定を再実装させないため）。
  - `journal` — 今日のジャーナルを `$EDITOR` で開く。`--print` でパスのみ出力。
  - `toggle <file> <line>` — 指定ファイル・行（1 始まり）のタスク状態を切り替え（`[ ]` → `[x]` → `[-]` → `[ ]` の3状態サイクル）。
  - `schedule` — 今日のスケジュールを表示。`--format json|yaml`、`--date YYYY-MM-DD` で日付指定。
  - `agents-md` — 同梱の AGENTS.md 内容を出力。`--output <path>` でファイル書き出し。
  - `resolve <name>` — `[[name]]` の対応ファイルパスを出力。無ければ作成（日付なら journal 配下、それ以外は `$HOME/taski/note/<name>.md`）。`--no-create` で作成抑止、`--format json` で構造化出力。
  - `pj` — PJ 横断の状態を表示（`list` が日付軸なのに対し PJ 軸）。`--format table|json`（既定 `table`）、`--status active,someday`（既定 `active`）、`--all` で `done` を含む全件（`--status` とは排他）、`--today YYYY-MM-DD` で基準日を指定、`--no-fetch` で `repo:` の fetch を省略。詳細は [6.1](#61-pj-サブコマンド)。
- **構造化出力の契約**: `--format json|yaml` を持つサブコマンド（`list` / `schedule`）は、該当 0 件でも空配列（`[]`）を返し、終了コードは 0 とする。呼び出し側が常にパースできるようにするためで、人間向けのテキスト表示のときだけメッセージを出す。0 件は正常系（タグに該当なし、予定の無い日）として普通に起きるので、そこでメッセージを返すとパースが 0 件のときだけ壊れる。
  - フォーマットの解釈は集計より前に済ませる。集計を先にすると「0 件だからメッセージを出して return」が先に走り、この契約が破れる。未対応フォーマットは 0 件でもエラー終了する。
  - `$HOME/taski` 自体が存在しない場合はエラー（終了コード 1）とする。この契約が保証するのは終了コード 0 のときの stdout。

### 6.1 `pj` サブコマンド

- 対象は `note/*.md` のうち front matter に `project:` を持つノート（[2.3](#23-pj-ノートの日報形式)）。`list` と違いサンプルタスクを拾わない。
- **判断はしない。** 機械的に決まる事実だけを出力し、粒度の妥当性や着手可否の判断は利用側（Claude Code の skill 等）に委ねる。
- 集約する指標:

| 指標 | 定義 |
| --- | --- |
| `next_action` | `## 次の予定` の最初の `- [ ]` 行。`next_action_body` / `next_action_meta` に分離して返す |
| `next_action_ai` | 判断メタデータのコンテキストに `@AI` を含むか |
| `health` | `no-next`（`- [ ]` が無い）/ `unclarified`（判断メタデータが無い）/ `ok` |
| `repo`・`repo_abs` | front matter の生値と、`~` 展開・シンボリックリンク解決済みの絶対パス |
| `updated`・`stale_days` | PJ ノート自体の最終更新日（git 基準）と経過日数 |
| `log_last`・`log_days` | `## ログ` の最新日付と経過日数 |
| `journal_last`・`journal_days` | journal で `[[名前]]` / `#タグ` により最後に**言及**された日と経過日数 |
| `journal_work_last`・`journal_work_days` | journal で最後に**実働**があった日と経過日数 |
| `repo_last`・`repo_days` | `repo:` のリポジトリの最終コミット日と経過日数 |
| `unreported`・`unreported_count` | `repo_last > log_last` のとき true。作業は進んでいるのにログに反映されていない状態 |
| `has_remote`・`ahead_count` | remote が設定されているか、remote に無いコミット数 |
| `backlog_count`・`backlog` | `## オープンタスク` の項目 |

- 停滞（`stale_days` / `log_days`）と言及（`journal_days`）は分けて保持する。合成すると「候補に載っただけで停滞 0 日」になり実態が見えなくなる。
- **言及（`journal_last`）と実働（`journal_work_last`）も同様に分ける。** 言及は `## 今日の候補` に載っただけ・他タスクの文中で触れられただけでも動くので、「本当に手が動いたか」を見る判定に使うと構造的に誤検出する。実働は、その PJ への参照（`[[名前]]` / `#タグ`）を持つタスク行が次のいずれかを満たす日とする。
  - `- [x]` で完了した → その journal の日付
  - 時刻付きログ（`- YYYY-MM-DD HH:MM: ...`）を持つ → そのログ行の日付
  - 時刻の無いログ（`- YYYY-MM-DD: ...`）は実働と見なさない。journal では予定・メモとしても書かれるため。`- [-]`（見送り＝着手せず）はそれ自体では実働にしない。ただし上の 2 条件は独立なので、見送りでも配下に時刻付きログがあれば実働とする（着手した時間の記録が残っている以上、チェックボックスの最終状態だけで捨てるのは誤り）。
  - 時刻付きログは**そのタスクの配下**（より深いインデント）にあるものだけを見る。見出し・兄弟の箇条書き・段落が挟まった時点でタスクの文脈は閉じる。`## 今日の候補` に PJ を並べ、別セクションに無関係な時刻付きログを書くのは journal の普通の形なので、ここを緩めると「候補に載せただけ」が実働に化けて分離の意味が無くなる。
  - **実働は言及の部分集合でなければならない。** 参照（`[[名前]]` / `#タグ`）の拾い方は両者で同一の実装を使う。片方だけが `[[名前.md]]` のような表記を拾うと「実働はあるのに言及が `null`」という成り立たない組み合わせが出る。
  - 実働日は走査順に依存させない。時刻付きログは自分の日付を持つため、新しい journal に前日ぶんの記録を書き足すと、新しい順に見て最初に見つかった日付が最大とは限らない。**最大値を採る。**
- `repo_abs` は `repo:` を `~` 展開しシンボリックリンクを解決した絶対パスとする。ディレクトリが存在しなければ `null`。利用側（セッションの `cwd` と PJ を突き合わせる等）に展開ロジックを再実装させないために出す。プロセスの `cwd` は解決済みの物理パスで報告されるので、それに揃える。
- `has_remote` は「リモートにバックアップがあるか」を示す。`repo:` が無い・パスが存在しない・git リポジトリでない場合は `null` とし、`false`（remote 未設定）と区別する。`repo:` を持たない PJ をバックアップ無しとして数えないため。
- `ahead_count` は remote に push されていないコミット数（ローカルの全ブランチから辿れて remote から辿れないもの、`--branches --not --remotes` 相当）。remote が無ければ `null`。ブランチごとの upstream 設定には依存させない。upstream 未設定の作業ブランチが数から漏れるうえ、全ブランチを見る `repo_last` と土俵が変わるため。
- `--today` は日付フィルタの基準日とする。基準日より後のログ・コミット・journal 言及・ノート更新は、まだ存在しないものとして集計から除外する（`log_last` などは基準日以前の最新を採り、無ければ `null`）。経過日数が負になってはならない。先の日付を書いたログや翌日ぶんの journal も同様に扱う。
  - 巻き戻るのは日付由来のフィールド（`log_last` / `repo_last` / `journal_last` / `journal_work_last` / `updated` と各日数、`ahead_count`、`logs`）だけ。`next_action` / `health` / `backlog` / `status` / `completed` はノートの現在の内容を出す（過去のノート内容は git から復元しない）。「その日時点のスナップショット」ではないので、ドキュメントでそう書かないこと。
- `unreported` の判定は厳密大なりなので、`log_last` 当日のコミットは反映済みと見なす。`unreported_count` も同じ比較で数え、フラグと件数を食い違わせないこと。
  - **フラグと件数は同一のクエリ結果から作る。** 件数だけ git 側（`--after`）に数えさせてはならない。日付の基準が食い違うため: `%ad` は author date をコミット自身のタイムゾーンで描画するのに対し、`--after` は committer date を実行環境のローカルタイムゾーンで解釈する。同じデータでも `TZ` によって件数が変わる。
  - `repo_last` も `git log -1` では取らない。`-1` は commit date 順の先頭 1 件から author date を出すので、rebase / cherry-pick で両者がずれると他のコミットより古い日付を返す。取得した日付の最大値を採る。
  - `## ログ` が 1 件も無い PJ は `log_last` が `null` なので、リポジトリの全コミットを未反映として数える（`unreported` が true であることと整合させる）。
- リポジトリの走査は HEAD ではなく `--branches --remotes` を対象とする（未マージの作業ブランチを取りこぼさないため）。`--all` は使わない（jj の `refs/jj/keep/*` を拾って件数が膨らむ）。リポジトリが存在しない・git でない場合は `null` を返して続行する。
- PJ ノートの最終更新日（`updated`）を git から取る際は `--relative` を付ける。付けないとパスがリポジトリルート相対で出るため、taski ディレクトリがリポジトリ直下でない配置（dotfiles リポジトリ配下など）で `note/*.md` と突き合わせられず、黙って `null` になる。
- `repo:` のリポジトリは既定で `git fetch` してから読む。fetch しない限り「ローカルの clone が古い」ことは検出できない（remote-tracking ref 自体が古く、比較対象にならない）ため、既定を fetch ありとする。
  - fetch は並列に流す。認証待ちで固まらないよう対話プロンプトを無効化し（`GIT_TERMINAL_PROMPT=0` / ssh は `BatchMode=yes`）、遅い接続や到達不能なホストで止まらないよう HTTP の低速打ち切りと SSH の接続タイムアウト（`ConnectTimeout`）を入れる。利用者が `GIT_SSH_COMMAND` を設定している場合は上書きしない。
  - リモートを持たないローカル専用リポジトリは fetch をスキップする。fetch に失敗しても集計は続行し、失敗したリポジトリを報告する（`fetch_failed`。table では警告行）。
  - `--no-fetch` で省略できる。即答性が要る用途（`next-action` 等）はこちらを使う。その場合 `repo` の日付はローカルの clone 基準になる。`ahead_count` も remote-tracking ref 基準なので同じ影響を受ける。
- `table` の並び順は手を入れる必要が高い順（未反映 → ログが古い/無い → `no-next` → `unclarified`）。日本語の桁揃えには東アジア文字幅を用いる。
- `table` は PJ 名の前に固定幅の印を出す（`!` 未反映 / `L` remote 未設定 / `^` 未 push コミットあり）。印の有無で桁がずれないよう幅は常に一定とし、端末によって幅の解釈が割れる全角文字は使わない。
