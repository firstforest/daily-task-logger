# taski 記法仕様

本ドキュメントは taski が読む Markdown の **書き方** を定める。

- **[requirements.md](requirements.md)** — *何を* 満たすか（要求）
- **[architecture.md](architecture.md)** — *どこに* 置くか（クレート構成・パイプライン・ビルド）
- **[domain.md](domain.md)** — *何が何であるか*（概念・関係・導出。目標形）
- **[design.md](design.md)** — *どう表しているか*（型・走査・不変条件・写像）
- **本ドキュメント** — *どう書くか*（文書・行・行内の記法）

**本ドキュメントは記法の唯一の規範である。** 他のドキュメントに記法の断片が現れる場合、正はここにある。要求の根拠（なぜその書式なのか）は requirements.md、走査の状態機械と Rust の型は design.md、概念としての意味は domain.md が持つ。

**§1〜§9 は現状の記法、§10 は目標形の記法である。** domain.md が概念の *目標形* を書くのに対し、記法は実装されているものを規範とする。domain.md の目標形（`Schedule` / `contexts` / `deadline` を Task が持つ）を書くための記法は §10 に定めてあるが、まだ実装されていない。

**記法は行の形だけで決まる。** セクション見出しの下にあるかどうかは、原則として行の種別を変えない。例外は 2 つだけで、どちらも本ドキュメントに明記してある（トップレベル時刻メモの発火条件 §3.4、PJ ノートのセクション規約 §8.2）。

## 1. 全体像

taski が読むのは Markdown だが、解釈するのは**行単位の限られた形**だけである。強調・リンク・表・リストのネスト・段落といった Markdown の一般構文は解釈せず、本文の文字列としてそのまま扱う。

記法は 3 つの層に分かれる。

| 層 | 何を決めるか | 節 |
| --- | --- | --- |
| 文書 | ファイルの位置と front matter が、その文書に何を与えるか | §2 |
| 行 | その行が何であるか（タスク・ログ・時刻メモ・見出し・その他） | §3・§4 |
| 行内 | 本文に埋め込む参照（`[[名前]]` / `#タグ`）と属性（行末の括弧） | §5 |

3 層は独立している。行の種別は文書の位置に依らず、行内の記法は行の種別に依らない（`[[名前]]` はタスク行にもログ行にも自由記述にも書ける）。

書ける要素の一覧:

| 要素 | 記法 | 節 |
| --- | --- | --- |
| タスク | `- [ ] 本文` / `- [x] 本文` / `- [-] 本文` | §3.1 |
| ログ | `- YYYY-MM-DD: 本文` | §3.2 |
| 時刻付きログ | `- YYYY-MM-DD HH:MM: 本文` / `- YYYY-MM-DD HH:MM-HH:MM: 本文` | §3.2 |
| 日付見出し | `# YYYY-MM-DD` | §3.3 |
| トップレベル時刻メモ | `- HH:MM: 本文` | §3.4 |
| Wiki リンク | `[[名前]]` | §5.1 |
| タグ | `#タグ` | §5.2 |
| 判断メタデータ | 行末の `（45分・重・@PC）` | §5.3 |
| front matter | `project:` / `repo:` / `completed:` | §2.2 |
| 解析除外 | ` ``` ` / `~~~` で囲む | §2.3 |

**この一覧は現状の記法である。** タスクの予定（いつやるか・どれくらいかかるか）・締切・コンテキストは、目標形ではタスクの配下に置く属性行として書く（§10）。

## 2. 文書

### 2.1 パス規約

| 種別 | パス | 与えるもの |
| --- | --- | --- |
| ジャーナル | `$HOME/taski/journal/<YYYY>/<MM>/<YYYY-MM-DD>.md` | その文書に書かれた記録の既定の日付 |
| ノート | `$HOME/taski/note/<名前>.md` | Wiki リンクの作成先の既定。PJ ノートの探索範囲 |

`$HOME/taski` を **taski home** と呼ぶ。ジャーナルの `<YYYY>` / `<MM>` は `<YYYY-MM-DD>` と一致していなければならない（`journal/2026/08/2026-08-02.md`）。中間ディレクトリは書き込み時に自動生成される。

**パスは日付を与えるだけで、記法を変えない。** ジャーナルでも一般のノートでも、タスク行・ログ行の書き方は同じである。パスによって振る舞いが変わるのはトップレベル時刻メモ（§3.4）と PJ ノートの探索（§8.2）だけで、どちらも記法そのものではなく「どの解析が走るか」の話である。

`note/` は Wiki リンクの作成先の既定であり、PJ ノートは `note/` **直下**（`note/*.md`）だけを探す。`note/sub/名前.md` は Wiki リンクとしては開けるが PJ としては拾われない（design.md G-5・G-6）。

### 2.2 front matter

ファイル先頭の YAML front matter で、その文書の役割を宣言する。

```markdown
---
project: active
repo: ~/workspace/dicegame
---
```

| キー | 値 | 意味 |
| --- | --- | --- |
| `project` | `active` / `someday` / `done` | この文書を PJ ノートにする。値は小文字のみ |
| `repo` | パス文字列 | 作業実体が別リポジトリにある場合のその場所。`~/` を展開する |
| `completed` | `YYYY-MM-DD` | `project: done` のときの完了日 |

構文規則:

- **1 行目が `---` でなければ front matter は無い。** 行末の空白は無視するが、行頭の空白は許さない。
- 2 行目以降の最初の `---` が終端になる。終端が無ければ front matter は無い。
- 本体が空白だけなら、キーを 1 つも持たない front matter として扱う。
- **YAML として不正なら front matter 全体が無効になる。** 一部のキーだけ拾うことはしない。
- 上の 3 キー以外は無視する。他のツール用のキーを書いてよい。

`project:` を書く行為そのものが Project を作る（domain.md §2）。`repo:` は「git の観測をどこに向けるか」の宣言であって、Project の性質ではない。

### 2.3 コードフェンス

` ``` ` または `~~~` で始まる行は**フェンス行**で、これに挟まれた範囲は全ての解析から除外される。

```ebnf
fence = indent , ( "```" | "~~~" ) , { any } ;
```

- 行頭のインデントを許す。
- 開始と終了を区別せず、フェンス行に出会うたびに内外が反転する。言語指定付きの開始行（` ```rust `）も同じ規則で拾う。
- ` ``` ` と `~~~` は区別しない。`~~~` で開いた範囲を ` ``` ` で閉じられる。

フェンスはタスクの文脈を切らない。タスクの配下にコードブロックを挟んでも、その後のログはそのタスクに帰属する（design.md §4）。

### 2.4 それ以外の行

上のどれにも当てはまらない行は**自由記述**である。段落・表・引用・ネストしたリストは、行の種別としては「その他」に落ちるだけで、エラーにはならない。自由記述に書いた `[[名前]]` / `#タグ` は参照として拾われる（§5）。

## 3. 行の文法

行の種別は次の文法で決まる。`digit` は ASCII 数字、`sp` は空白 1 文字（半角スペースまたはタブ）。

```ebnf
line       = fence | heading | task | log | time_memo | bullet | other ;

fence      = indent , ( "```" | "~~~" ) , { any } ;
heading    = "#" × 1..6 , sp+ , text ;
date_head  = "#" , sp+ , date , { any } ;                 (* heading の部分集合。§3.3 *)
task       = indent , "-" , sp* , "[" , marker , "]" , sp* , text ;
marker     = " " | "x" | "-" ;
log        = indent , "-" , sp* , date , [ sp+ , time , [ "-" , time ] ] , ":" , sp* , text ;
time_memo  = "-" , sp , time , ":" , sp , text⁺ ;         (* インデント不可・トップレベルのみ *)
bullet     = indent , "-" , sp+ , text ;

date       = digit × 4 , "-" , digit × 2 , "-" , digit × 2 ;
time       = digit × 1..2 , ":" , digit × 2 ;
indent     = { " " | "\t" } ;
```

判定は上から順で、最初に一致した種別になる。`fence` が最優先で、フェンスの内側では以降のすべてを無視する。`task` が `log` より先なので、`- [ ] 2026-08-01 の件` はタスクであってログではない。`bullet` は `task` にも `log` にも一致しなかった箇条書きを指す。

**リストマーカーは `-` だけである。** `* ` / `+ ` / `1. ` で始まる行はタスクにもログにもならない。

### 3.1 タスク行

```markdown
- [ ] 買い物リストを作る
- [x] 資料を送る
- [-] 打ち合わせの準備
```

| マーカー | 状態 | 意味 |
| --- | --- | --- |
| 半角空白 | 未完了 | まだ終わっていない |
| `x` | 完了 | 終わった |
| `-` | 見送り | 着手予定だったが着手しなかった。やらないと決めたか、別の場所に積み替えた |

規則:

- マーカーは `[` と `]` に挟まれた**ちょうど 1 文字**で、`[ x-]` の 3 つに限る。`[X]` や `[ok]` は一致しない。
- 行頭のインデントは任意。インデントの深さはログの帰属（§4）にだけ効く。
- `]` の後の空白は 0 個以上。本文が空の `- [ ]` も（本文が空文字列の）タスク行として一致する。
- 3 状態は `未完了 → 完了 → 見送り → 未完了` の順にトグルする（`taski toggle` / `taski.toggleTask`）。トグルはマーカーだけを書き換え、インデント・本文・行内の位置を保つ。

**`- [[ノート名]] ...` はタスクではない。** `[` の次が `[` なのでマーカーの 1 文字に一致しない。これは偶然ではなく要求であり、判定を緩めてはならない（requirements.md 2.3）。

### 3.2 ログ行

```markdown
- [ ] 記事を書く
    - 2026-08-01: 構成を決めた
    - 2026-08-02 10:00: 執筆開始
    - 2026-08-02 13:00-14:30: 推敲
```

- 日付は `YYYY-MM-DD` の固定桁で、省略できない。
- 時刻は任意。書くときは日付との間を空白 1 個以上で区切る。
- 終了時刻は `-` で続けて書く。区切りの前後に空白は入れられない（`10:00 - 11:00` は一致しない）。
- 日付（と時刻）の直後の `:` は必須。その後の空白は 0 個以上で、本文は空でもよい。
- **タスク行より深くインデントすると、そのタスクのログになる**（§4）。

時刻の有無は意味を持つ。時刻付きログだけが実働の証拠として数えられ、時刻なしログは予定・メモとしても書かれるため実働にならない（requirements.md 6.1）。

**日付・時刻の妥当性は検証しない。** `2026-13-45` や `99:99` も構文としては通る（N-1）。

### 3.3 日付見出し

```markdown
# 2026-08-02
```

ジャーナルで使う、その日の記録の始まりを示す見出し。

- **レベル 1 の見出しだけ**が日付見出しになる。`## 2026-08-02` は日付見出しではない。
- 行頭に空白を置けない。
- 日付の後ろに文字を続けてよい（`# 2026-08-02 土曜`）。

日付見出しが与えるのは、同じ文書のトップレベル時刻メモの日付だけである（§3.4）。タスク行やログ行がここから日付を受け取ることはない — ログ行は必ず自分で日付を書く。

見出し（レベルを問わず）は走査中の文脈としてスタックに積まれ、タスクの `context` になる。日付見出しを含め、見出しはタスクの文脈を閉じない（design.md §4 R3）。

### 3.4 トップレベル時刻メモ

```markdown
# 2026-08-02

- 09:00: 朝会
- 14:00: 病院
```

タスクに紐づかない、その日の予定・出来事を書く記法。

- **行頭に空白を置けない。** インデントされた `- 10:00: ...` は時刻メモではない（タスクのログでもない — 日付が無いため、単なる箇条書きになる）。
- `-` の後と `:` の後の空白は、**それぞれちょうど 1 個**でなければならない。
- 本文は 1 文字以上必要。
- **終了時刻を書けない。** `- 10:00-11:00: 会議` は一致しない。開始終了を書きたい場合はタスク配下のログ行（§3.2）を使う（N-8）。

**発火条件**: その文書のどこかに、対象日と一致する日付見出し（§3.3）があること。この条件を満たすと、**その文書のトップレベル時刻メモがすべて**対象日の項目として扱われる。見出しより後ろにあることは要求されない（N-5）。

日付見出しから日付を受け取るのはこの記法だけで、他のすべての記法は日付を自分で書く（domain.md §1）。

### 3.5 箇条書き

`task` にも `log` にも一致しない `- ` 始まりの行。`-` の後に空白が 1 個以上必要（`-foo` は箇条書きではない）。

一般の文書では単なる自由記述として扱われる。PJ ノートの `## オープンタスク` セクションでだけ、バックログの項目として抽出される（§8.2）。

## 4. インデントと帰属

**ログはタスクより深くインデントすることで、そのタスクのログになる。**

```markdown
- [ ] 記事を書く
    - 2026-08-01: 構成を決めた      ← このタスクのログ
- 2026-08-01: 別の記録              ← 同じ深さなのでタスクのログではない
```

- 比較は**厳密大なり**である。同じ深さの `- YYYY-MM-DD: ...` はタスクの兄弟であって、ログではない。
- インデントの幅は**バイト数**で数え、タブは 1 と数える。タブと空白を混在させると意図しない深さになる（design.md §2）。
- 直前のタスクに帰属する。間に見出しや段落を挟んでも、通常の解析では帰属は切れない。

**実働の判定（`taski pj`）だけは、より厳しい帰属規則を使う。** 空でない行のインデントがタスク以下になった時点でそのタスクの文脈が閉じる。ジャーナルは候補リストと無関係な時刻メモが同居する形が普通なので、緩い規則のままだと「候補に載せただけ」が実働に化けるためである（design.md §4）。

書き手から見た帰結は 1 つで、**あるタスクのログとして扱わせたい行は、そのタスクの下に、より深いインデントで、間に浅い行を挟まずに置く**。この書き方をしていれば 2 つの規則は一致する。

## 5. 行内の記法

行内の記法は本文の任意の位置に書ける。タスク行・ログ行・自由記述のどれに書いても同じように認識される。

### 5.1 Wiki リンク

```markdown
[[在庫管理]] の件を進める
```

- `[[` と `]]` に挟まれた 1 文字以上の文字列。`[`・`]`・`|` を含められない。
- **表示名付き（`[[名前|表示]]`）は認識しない。** `|` を含むためリンクとして拾われず、参照にもならない（N-7）。
- 名前は前後の空白を落とし、末尾の `.md` を除いて正規化する（`[[ foo.md ]]` と `[[foo]]` は同じ）。
- 名前が `YYYY-MM-DD` の形ならジャーナルを指す。それ以外はノートを指す。

解決先が存在しない場合の作成先:

| 名前 | 作成先 | 初期内容 |
| --- | --- | --- |
| `YYYY-MM-DD` | `$HOME/taski/journal/<YYYY>/<MM>/<YYYY-MM-DD>.md` | `# <名前>` |
| それ以外 | `$HOME/taski/note/<名前>.md` | `# <名前>` |

**解決先が無い Wiki リンクを書いてもよい。** 参照は解決を前提としない（domain.md §3 層 3）。

### 5.2 タグ

```markdown
- [ ] 牛乳を買う #買い物
```

- `#` に続く、**空白と `#` を含まない 1 文字以上**の文字列。
- 行内のどこに書いてもよい。
- 前後の文脈を見ないので、URL の `#fragment` のような意図しない文字列も拾う（N-2）。
- 区切りが空白と `#` だけなので、句読点は名前の一部になる（`#買い物。` のタグ名は `買い物。`）。

タグには 2 つの出どころがある。

| 出どころ | 規則 |
| --- | --- |
| 本文 | 上の `#タグ` |
| ファイル | front matter に `project: active` があるとき、そのファイル名（`.md` を除き、空白を `_` に置換）を、その文書の全タスクに付与する |

両者は合算される。`project` が未指定・`someday`・`done` の場合はファイル由来のタグを付けない（requirements.md 2.2。この条件は層をまたいだ依存であり、いずれ表示側の責務に移す — design.md G-1）。

### 5.3 行末の括弧（判断メタデータ）

```markdown
- [ ] 続きを実装する（30分・重・@PC）
```

行末の括弧に、そのタスクについての判断材料を書く。

構文:

- 括弧は行末になければならない（後続は空白のみ）。
- 全角 `（）` と半角 `()` のどちらでもよい。**開きと閉じが揃っている必要はない**（`（45分)` も通る — N-3）。
- 中身は括弧を含まない 1〜60 文字。ネストできない。
- 1 行に複数の括弧があるときは**最後の括弧**を見る。

中身を `・` `,` `、` `，` で分割し、**いずれか 1 要素**が次のどれかに一致するときだけ、括弧全体を判断メタデータとして本文から分離する。各要素は前後の空白を落としてから判定する。

| 要素 | 書式 | 例 |
| --- | --- | --- |
| 所要時間 | `<数字>分` / `<数字>時間`（数字と単位の間に空白可） | `45分` `2時間` |
| 重さ | `軽` / `重` のいずれか | `重` |
| コンテキスト | `@` + 1 文字以上 | `@PC` `@AI` `@家` |
| 締切 | `<1〜2桁>-<1〜2桁>`（`締切` 接頭辞は任意） | `08-15` `締切08-15` |

**「いずれか 1 要素」で足りるとしているのは、一部だけ書く運用を許すためである。** 全要素を要求すると `（45分・重）` のような通常の書き方を落とす。逆にこの条件があるおかげで、単なる注記（`（仮）`）や列挙（`（髪・服・顔）`）は分離されない。

分離した結果は本文（`body`）とメタデータ（`meta`）として構造化出力に載る。**利用側で切り出し直さず、このフィールドを使うこと。**

**現状、メタデータは分割されない文字列のまま返る。** `45分` も `08-15` も「メタデータらしさ」の判定に使われるだけで、値としては解釈されない。所要時間・コンテキスト・締切を Task の属性にするのが目標形で、そのとき `meta` という概念は消える（domain.md §1・design.md G-12）。

**目標形ではこの記法は属性行（§10）に置き換わる。** 括弧の中に要素を並べるのをやめ、タスクの配下にキー付きの行として書く。

## 6. 正規化と照合

| 対象 | 規則 |
| --- | --- |
| 時刻 | 1 桁時を 2 桁にパディングする（`9:30` → `09:30`）。正規化後は必ず `HH:MM` の 5 文字 |
| Wiki リンクの名前 | 前後の空白を落とし、末尾の `.md` を除く |
| 照合キー | 空白を `_` に置換する |

**照合キーは `[[名前]]` と `#タグ` を突き合わせるために要る。** `#タグ` には空白を書けないので、空白を含む PJ 名は `_` で代用する。

| 表記 | 例 | 空白 |
| --- | --- | --- |
| `[[名前]]` | `[[在庫 管理]]` | 書ける |
| `#タグ` | `#在庫_管理` | 書けない（`_` で代用する） |

この変換は非可逆で、`在庫 管理` と `在庫_管理` は同じ照合キーになる。**PJ ノートの名前は、照合キーが衝突しないように付けること**（domain.md §4）。

## 7. 誤検出しない書き方

**次の書き方が解析対象にならないことは仕様である。** 判定を緩めてはならない。

| 書き方 | 何にならないか | 理由 |
| --- | --- | --- |
| `- [[ノート名]] について` | タスクにならない | マーカーは `[ x-]` の 1 文字だけ（§3.1） |
| `（仮）` `（髪・服・顔）` | 判断メタデータにならない | どの要素も書式に一致しない（§5.3） |
| `* [ ] 本文` `1. [ ] 本文` | タスクにならない | リストマーカーは `-` だけ（§3） |
| `[[名前\|表示]]` | Wiki リンク・参照にならない | `|` を含む（§5.1） |
| ` ``` ` で囲んだ範囲 | 何にもならない | フェンス内は全解析から除外（§2.3） |
| `## 2026-08-02` | 日付見出しにならない | レベル 1 だけ（§3.3） |
| 同じ深さの `- YYYY-MM-DD: ...` | そのタスクのログにならない | 帰属は厳密大なり（§4） |
| インデントされた `- 10:00: 本文` | 時刻メモにならない | トップレベルのみ（§3.4） |

## 8. 文脈ごとの適用範囲

記法そのものはどの文書でも同じだが、**どの解析が走るか**は文書の位置と front matter で決まる。

### 8.1 解析ごとに読む記法

| 解析 | 対象文書 | 読む記法 |
| --- | --- | --- |
| 日付別ビュー / `taski list` | スキャン対象の全 md | タスク行・ログ行・見出し（文脈）・行末括弧 |
| タグ別ビュー / `--tag` | 同上 | 本文の `#タグ` + front matter `project: active` によるファイル名タグ |
| スケジュール / `taski schedule` | 同上 | タスク行・時刻付きログ行 + 日付見出し・トップレベル時刻メモ |
| `taski pj`（ノート側） | `note/*.md` のうち `project:` 持ち | front matter・`#`/`##` セクション・タスク行・ログ行・箇条書き・行末括弧 |
| `taski pj`（ジャーナル側） | `journal/**/*.md` | タスク行・時刻付きログ行・`[[名前]]`・`#タグ` |
| Wiki リンク | 編集中の md | `[[名前]]` |

スキャン対象は taski home と、設定で加えたディレクトリ・ワークスペース・開いている文書である（requirements.md 4）。

### 8.2 PJ ノートのセクション規約

**PJ ノート（front matter に `project:` を持つ `note/*.md`）にだけ、セクションによる規約がある。**

```markdown
---
project: active
---

# 在庫管理

## 次の予定
- [ ] 棚卸しの手順を決める（30分・@PC）

## ログ
- 2026-08-01: 現状の棚卸し手順を確認した

## オープンタスク
- 発注フローの見直し
```

| セクション | 記法 | 役割 |
| --- | --- | --- |
| `## 次の予定` | タスク行（§3.1） | 唯一の Next Action。最初の未完了タスク 1 行だけを見る |
| `## ログ` | ログ行（§3.2） | 日々の記録 |
| `## オープンタスク` | 箇条書き（§3.5） | バックログ。タスクとしては解析しない |

- セクションの範囲は次の `#` または `##` 見出しまで。`###` 以下は直前のセクションに含める（`## オープンタスク` を `###` でグループ分けしてよい）。
- 見出し文字列は完全一致で探す。
- **チェックボックスを持つのは `## 次の予定` だけ**とする。この規約により、PJ 由来で `taski list` に流れ込むタスクが active な PJ あたり高々 1 件に抑えられる。

**このセクション規約は暫定である。** ドメイン上、セクションは構造ではなく人が文書を整理する道具であり、モデルが見出し文字列に依存すべきではない（domain.md §2）。目標形ではセクションによる絞り込みをやめ、ノート全体からタスクとログを拾う。そのとき「チェックボックスは `## 次の予定` だけ」という制約も、`next_action` / `backlog` という概念も消える（design.md G-10）。

## 9. 記法の弱さ

**型でもテストでも守っていないが、そう決めた**箇所を挙げる。design.md の W-*（実装の弱さ）・G-*（ドメインとのずれ）と対応するものは併記する。

- **N-1 日付・時刻の妥当性を検証しない。** `2026-13-45` や `99:99` は構文として通る。不正な日付は日数計算の段階で初めて落ちる（design.md W-1）。
- **N-2 タグの区切りが空白と `#` だけである。** 句読点がタグ名に入り（`#買い物。`）、URL の `#fragment` や、Markdown 見出しの `#` に続く文字列も拾いうる。
- **N-3 行末の括弧は全角と半角が揃っていなくてもよい。** `（45分)` が通る。揃える判定にすると、日本語入力で片方だけ半角になった行を落とすため。
- **N-4 対応の取れないフェンスが 1 つあると、それ以降がすべて解析対象外になる。** フェンスは開始・終了を区別せず反転するだけなので、閉じ忘れた文書は残り全体が無視される。
- **N-5 トップレベル時刻メモは日付見出しの「配下」ではなく、文書全体で有効になる。** 対象日と一致する日付見出しが文書のどこかにあれば、その文書のトップレベル時刻メモをすべて拾う。1 つの文書に複数の日付見出しを書くと、両方の日の時刻メモが混ざる。ジャーナルが 1 ファイル 1 日である限り表面化しない。
- **N-6 `- [ ]` の `-` と `[` の間に空白が無くてもよい。** `-[x] 本文` がタスクとして通る。
- **N-7 表示名付き Wiki リンク（`[[名前|表示]]`）を認識しない。** リンクとして開けず、参照にもならない。
- **N-8 トップレベル時刻メモに終了時刻を書けない。** ログ行は `10:00-11:00` を書けるが、時刻メモは開始時刻だけである。予定の長さを書きたい場合はタスクとその配下のログにする。
- **N-9 判断メタデータの中身を分割した結果を捨てている。** 「メタデータらしさ」の判定にしか使われず、所要時間・締切が値として解釈されない（design.md G-12）。

## 10. 目標形の記法 — 属性行

**domain.md の目標形（Task が `schedule` / `contexts` / `deadline` を持つ）を書くための記法は、タスクの配下に置く属性行とする。** 行末の括弧（§5.3）を拡張するのではなく、書く場所を変える。

**本節はまだ実装されていない。** 実装した時点で §3 に昇格させ、§5.3 の括弧記法を置き換える（design.md G-11・G-12）。

### 10.1 書き方

```markdown
- [ ] 棚卸しの手順を決める
    - 予定: 2026-08-01 10:00
    - 所要: 45分
    - 締切: 2026-08-15
    - 文脈: @PC
    - 2026-08-01 10:05: 着手した
```

属性行はログ行と同じく**タスクの配下**（インデント厳密大なり）に置く。ログ行との順序は問わない。

### 10.2 構文

```ebnf
attr       = indent , "-" , sp* , attr_key , colon , sp* , attr_value ;
attr_key   = "予定" | "所要" | "締切" | "文脈" ;
colon      = ":" | "：" ;

予定の値   = date , [ sp+ , time , [ "-" , time ] ] ;
所要の値   = digit+ , sp* , ( "分" | "時間" ) ;
締切の値   = date ;
文脈の値   = context , { sp+ , context } ;
context    = "@" , ? 空白を含まない 1 文字以上 ? ;
```

- **日付で始まればログ行、既知のキーで始まれば属性行**であり、両者は排他である。判定の順序に依存しない。
- コロンは半角 `:` を規範とし、全角 `：` も受け付ける。日本語入力では全角が出やすいため。
- **既知のキー以外は属性行ではない。** `- 場所: 会議室` は自由記述の箇条書きになる。キーを開いた集合にすると、普通の箇条書き（`- 手順: まず棚を数える`）と区別がつかなくなるため。

### 10.3 ドメインへの写像

| 書き方 | 生成される値 |
| --- | --- |
| `- 予定: 2026-08-01` | `schedule.when = Day(2026-08-01)` |
| `- 予定: 2026-08-01 10:00` | `schedule.when = Moment(2026-08-01, 10:00)` |
| `- 予定: 2026-08-01 10:00-11:00` | `schedule.when = Moment(2026-08-01, 10:00)` と `schedule.duration = 60分` |
| `- 所要: 45分` | `schedule.duration = 45分` |
| `- 締切: 2026-08-15` | `deadline = 2026-08-15` |
| `- 文脈: @PC @AI` | `contexts = { PC, AI }` |

同じキーが複数行あるときの規則:

- `予定` / `所要` / `締切` は `Option` なので**最初の 1 行**を採る。
- `文脈` は `Set` なので**全行の和集合**を採る。複数行に分けて書いてよい。
- `予定` に終了時刻を書き、かつ `所要` も書いた場合は**終了時刻から導出した長さ**を採る。終了時刻は `duration` の別表記であり（domain.md §1）、より具体的な方を残す。

### 10.4 この形にすると消えるもの

行末の括弧を拡張する案が抱えていた 4 つの未決が、いずれも問題として成立しなくなる。

| かつての論点 | なぜ消えるか |
| --- | --- |
| 予定日と締切の衝突 | キーで区別する。`08-01` がどちらの意味か判別できない状況が起きない |
| 締切の年の補完 | フル日付を書く。`08-15` という省略形を持たない |
| 時刻の書き方 | `予定` の値の一部として書く。開始と終了も同じ行に収まる |
| 認識できない要素 | キーが一致しない行は属性行ではない。「残差」という概念が要らない |

加えて、**属性を後から増やしても行の形が崩れない。** 括弧の中に要素を並べる形は、要素が増えるほど「どれが属性でどれが注記か」の判定が重くなる（§5.3 の判定述語はそのために要る）。キーで書けば判定は完全一致 1 回で済む。

帰属の規則も新しく作らない。ログ行と同じ「タスクの配下」であり、§4 がそのまま効く。

### 10.5 現行記法との関係

| | 現行（§5.3） | 目標（本節） |
| --- | --- | --- |
| 場所 | タスク行の行末 | タスクの配下 |
| いつやるか | **書けない**（配下の日付行が兼ねる） | `- 予定: 2026-08-01 10:00` |
| 所要時間 | `（45分）` | `- 所要: 45分` |
| コンテキスト | `（@PC）` | `- 文脈: @PC` |
| 締切 | `（08-15）` / `（締切08-15）` | `- 締切: 2026-08-15` |
| 重さ | `（軽）` / `（重）` | **持たない**（domain.md §1） |

**移行には既存ノートの書き換えが要る。** 括弧の解釈をやめると、`（重）` としか書いていないタスクは括弧が本文に残る。所要時間・コンテキスト・締切を書いたタスクも属性行に移す必要がある。両記法を並行して受け付ける期間を設けるかは実装時に決める（design.md G-12）。

**本文中に裸の `@PC` を書いてもコンテキストにはならない。** `#タグ`（§5.2）が前後の文脈を見ずに拾うために誤検出を抱えている（N-2）のと同じ弱さを、新しい記法で増やさないため。コンテキストは属性行に書く。
